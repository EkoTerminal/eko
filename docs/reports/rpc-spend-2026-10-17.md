# Paid RPC attribution and reductions

This is a code-derived call inventory, not a claim that production method totals determine the traffic mix. One JSON-RPC batch with N entries is still N paid calls. Only Multicall3 replaces several `eth_call` entries with one. Retries and public-to-paid fallback attempts each count separately; cache hits do not enter the meter.

Independent pinned server getters are coalesced per microtask, block and urgency class, with per-getter failures preserved. Account overrides, state overrides, simulations and latest/pending reads bypass this coalescing. Large groups can be split by viem's calldata batch bound. Local Anvil `eth_call`/`getCode` calls in the live-trade implementation do not directly enter this paid meter; any lazy fork state comes through the separately metered fork gateway.

## Cache validity and intentionally retained reads

`rpc_code_cache` stores nonempty, non-7702 runtime code by address, its first usable observation block and canonical hash. It has no TTL. Earlier checkpoints, orphaned anchors, unknown block hashes, latest/pending selectors and empty/delegated accounts fall back to RPC. Indexed 7702 changes invalidate reuse. Both block-number and known canonical EIP-1898 hash pins are supported. Canonical anchor removal also causes a conservative miss.

`balances` alone is not proof of an absolute balance: the preexisting bag tests explicitly distinguish net observed transfer deltas from balances. Live log ingest now records `token_balance_origins` only for a launch whose mint was included in that fully acquired block. A canonical origin, a committed head-log cursor through the requested block and a maintained row not newer than the requested block are required. Historical partial tokens fall back to RPC. Coverage begins prospectively; no legacy balances are silently certified.

Owner powers are derived from the cached immutable bytecode; same-checkpoint getter observations already persist in `engine_reads`. **TODO(spec):** cross-block fee/getter reuse requires complete setter/upgrade event coverage and a verified anti-snipe time schedule. The current decoder names only launch, trades and exemptions; `currentSnipeTaxBps` can change with time. Reusing these getters until one of those events would change ratings, so that optimization is deferred. No TTL is introduced as a substitute for invalidation.

## Shared paid admission

Application roles use a SQL-serialized `rpc_paid_daily` call ledger, independent of method weights, in the same database as `rpc_usage`. Initial admission seeds existing paid method-call totals conservatively as non-indexer spend. Scheduling/status reads do not insert budget rows. HTTP attempts, retries, fallback attempts and already-billed socket notifications are counted. Public attempts never consume paid allowance. With application-role call admission active, unit leases are bypassed so one idle role cannot reserve the indexer's remaining calls. Legacy standalone meters without an application role retain their weighted-unit contract.

- `RPC_PAID_DAILY_SOFT_LIMIT`: 500000. At this total, routine engines/worker paid work is deferred. Listed first ratings and measured crash rechecks remain eligible.
- `RPC_PAID_INDEXER_RESERVE`: 300000. All non-indexer roles together can consume at most hard ceiling minus reserve, including urgent work. The indexer can consume the remaining total allowance.
- `RPC_PAID_DAILY_BUDGET`: hard call ceiling for application roles; when unset, soft limit + reserve (800000 by default). An existing explicitly configured lower value still wins and may leave no non-indexer allowance; update deployment settings deliberately. The example now includes all three settings.
- UTC rollover automatically reopens admission. The meter remains running after deferral; each process emits at most one `rpc_paid_ceiling_degraded` line per minute. Durable fee/sell-check evidence is not replaced with a fabricated successful reading.

## Daily projection

The five supplied paid categories sum to **636223 calls** (236085 indexing + 367557 calls + 32581 code reads), excluding any other paid methods. Method totals do not reveal evaluation counts or cache hit rates.

For the same workload: `projected = 636223 - 2*G - H - B - 2*M - sum(pool-discovery savings) - 3*C - A`.
Here G is worker Pons profiles that previously lost batching, H is eligible code-cache hits, B is covered bag balance reads, M is metadata loads, C is explicit control acquisitions, and A is additional non-overlapping pinned server batching savings. Pool discovery saves 3 calls with no pools, or K+2 with K>0 pools. Do not subtract the same getter twice.

Illustrative steady state only: if all 32581 code reads were repeat Pons evaluations and each lost the three-getter batch, savings would be 97743 and these categories would fall to **538480/day**, before the additional worker/server reductions. New-address code misses, actual origin shares, failures and cache coverage must be measured in production; a precise forecast or a promise of less than 500000 for the same ratings is not supported by the supplied totals. The ceiling is additional degradation, not part of the same-ratings savings estimate.
